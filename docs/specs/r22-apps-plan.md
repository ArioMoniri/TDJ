# Round 22 — macOS and iPadOS apps, release automation, store assets

Status: plan (2026-11-14). Owner checklist: [docs/APPLE_SETUP.md](../APPLE_SETUP.md). Models/ACP: [r22-acp-plan.md](r22-acp-plan.md). Roadmap items: ROADMAP "Round 22 onward" §6 (connections, models), §8 (native feel), §9 (apps and release).

Goal from the DJ: a macOS app and an iPadOS app with **every** web feature (composer, Booth player with audio, exports, Spotify/Deezer/Google/Dropbox connections, Database, Settings), shipped automatically to TestFlight and the App Store, a notarised macOS download on GitHub Releases with a "Download for macOS" button in the README, and store screenshots/metadata generated by CI in English and Turkish for designers to review.

Hard constraints: the agent container is Linux (no Xcode), so everything Apple-specific builds on GitHub-hosted macOS runners; signing material lives only in GitHub Actions secrets added by the owner; user keys stay BYOK and are never persisted server-side; the server, where needed, is the existing SST/OpenNext stack deployed by "Deploy to AWS" (OIDC).

So the app is **not** a static site: it is a client that leans on ~20 server routes plus browser-only media APIs. Any wrapper must answer three questions: where the server runs, how cookies/sessions survive a non-browser origin, and which media APIs survive WebKit.

## 2. Platform facts that decide the design (checked 2026-11)

- **Every wrapper on iPadOS is WKWebView** (WebKit). Only Electron/Chromium on macOS escapes WebKit. Safari/WKWebView facts:
  - Web Audio: full `AudioContext`, `decodeAudioData`, `AudioWorklet` — fine. Needs a user gesture to start (already true on the web). iPadOS: set the native `AVAudioSession` category to `.playback` from the shell, or the ringer switch mutes Web Audio.
  - `AudioContext.setSinkId`: **not in WebKit** (MDN compat lists Safari "No"). `HTMLMediaElement.setSinkId` arrived in Safari/iPadOS 26 (LiveKit's change log, Aug 2025; a WebKit bug fixed in July 2026 shows it was still flaky on iOS). Whether WKWebView exposes it to an app is **unverified** → spike S2. Plan for a native cue output instead (§4.3).
  - `showDirectoryPicker` / File System Access: **not in WebKit**. `<input webkitdirectory>` works on macOS WKWebView only with a native open-panel delegate; on iPadOS it is unreliable. → native folder plugin with security-scoped bookmarks (§4.2).
  - Spotify Web Playback SDK: Spotify supports it on **desktop** browsers only. Mobile Safari/WKWebView reports in the Spotify developer forum are inconsistent at best (activation, autoplay, background stop); Widevine does not exist in WebKit, so the SDK relies on FairPlay paths that Spotify does not promise in an embedded WKWebView. Treat it as **unsupported on iPadOS** and **unverified in a macOS WKWebView** → spike S1.
  - Google OAuth refuses embedded web views (`disallowed_useragent`). Any Google login must go through `ASWebAuthenticationSession` (system browser sheet). Spotify and Dropbox tolerate a web view but the same native sheet is better (password managers, passkeys, SSO with the Spotify app).
  - Third-party cookies: a page served from `tauri://localhost` (or any custom scheme) calling `https://<cloudfront>` gets **no cookies** (WebKit ITP blocks third-party cookies). Our sealed cookie sessions only work if the web view's top-level origin **is** the backend origin, or if the app switches to a header-borne session.
  - Downloads: WKWebView does not save `<a download>` blobs without a native `WKDownloadDelegate`; route exports through a native save panel (macOS) / share sheet (iPadOS).
  - Screen Wake Lock: in WebKit since 16.4; on iPadOS use the native `isIdleTimerDisabled` to be safe. Media Session: present in Safari; for Control Center/Touch Bar/hardware keys a native `MPNowPlayingInfoCenter` bridge is more reliable.
- **App Review**: guideline 4.2 (minimum functionality) rejects "a website in a box"; 2.5.2 forbids downloading executable code that changes features. A shell that loads a remote URL is accepted when it adds real native value (native audio routing, file bookmarks, Spotify app control, menus, keyboard, share sheet), but bundled UI is the safer final state.
- **Mac App Store** requires App Sandbox: user-selected file access + bookmarks are fine; outgoing network is fine (`com.apple.security.network.client`); **spawning arbitrary user-installed binaries (Claude Code, Gemini CLI) is not** — a sandboxed child inherits the sandbox and cannot reach the user's `$HOME`/tools. The Developer ID (DMG) build is not sandboxed. This matters for ACP (r22-acp-plan.md §4).
- **Runners**: GitHub-hosted macOS runners are free for public repositories; on private repositories macOS minutes count with the macOS multiplier (10× Linux at the time of writing — check "Billing → Actions" for the current figure). Do everything that does not need Xcode (lint, Rust checks, screenshots, metadata upload) on `ubuntu-latest`.
- **Toolchain**: since April 2026 App Store uploads must be built with the Xcode 26 / iOS 26 SDK. Use the `macos-26` runner image (or `macos-15` + `maxim-lobanov/setup-xcode` pinned to 26.x) — verify the label when the workflow is written.

**Choice: A — Tauri 2 for both macOS and iPadOS**, loading the TDJ backend origin in phase 1 and a bundled UI in phase 2, with five small native plugins. Reasons:

1. One shell, one plugin API (`invoke`), one CI pipeline for both platforms — the DJ asked for feature parity on both, which Capacitor+Electron would split in two.
2. The Rust core and the desktop plugins compile, lint and unit-test on Linux (this container and `ubuntu-latest`), so agents can keep working on most of the native code; only the Swift iOS plugin and final signing need macOS minutes.
3. The places where WebKit falls short (Spotify SDK, `setSinkId`, folders, downloads, OAuth) need native code in **every** WebKit option (A, B, E); Tauri keeps that code small and shared.
4. Plan B is documented and cheap to switch to: if spike S1 shows the Spotify Web Playback SDK is unusable in a macOS WKWebView *and* the DJ needs in-app Spotify audio on the Mac, add an Electron (castlabs) **macOS-only** build of the same remote-origin shell (option C). The web code's native adapters (§4) are wrapper-agnostic, so nothing else changes.

### 3.1 Where the server runs: "remote origin" first, "bundled UI" second

- **Phase 1 — remote origin (ship first).** The Tauri window's top-level URL is the TDJ backend: the production CloudFront URL by default, or a **self-hosted instance** the DJ enters in onboarding (or opens from a `tdj://server?url=…` link / QR code shown on `/admin`). Because the page is first-party, the sealed cookies, `guard.ts`, `/api/*`, SSM-held connector secrets and BYOK headers all keep working with **zero changes to the server**. Tauri 2 grants IPC to a remote origin only through a capability with `remote.urls`; the production origin is in the static capability, a self-hosted origin is added at runtime after an explicit "Trust this server?" confirmation (`app.add_capability`). An offline launch shows a native "Can't reach your TDJ server" screen with the last plan from IndexedDB still playable in the Booth (local files need no server).
- **Phase 2 — bundled UI + remote API (before App Store public release, or if review asks).** A static client build packaged in the app (`tauri://localhost`), talking to the same backend through `NEXT_PUBLIC_API_BASE`. Server work, all additive: CORS for the app origins (`tauri://localhost`, `http://tauri.localhost`), an `Authorization: TDJ-Session <sealed>` header accepted wherever a sealed cookie is read today (the app keeps the blob in the Keychain; still nothing stored server-side), and `guard.ts` accepting the app origins. Composition could later move client-side (`@tdj/core` is pure TS) for offline composing.
- **Optional phase 3 (macOS only)**: a Node sidecar running the Next standalone server on `127.0.0.1` for a fully offline Mac (connector logins still go through the deployed backend, because client secrets must never ship in an app).

No new AWS resources are required for phase 1. Phase 2 adds only route changes in the same SST `Nextjs` function. The release workflows never touch AWS.

## 4. Native plugins (the parity work)

The web app gets one new module, `apps/web/src/lib/native/` (feature-detects `window.__TAURI_INTERNALS__`), with adapters that fall back to the current web path when absent, so the browser build is unchanged.

| Plugin | macOS | iPadOS | Web fallback |
|---|---|---|---|
| `tdj-auth` | `ASWebAuthenticationSession` for Spotify/Google/Dropbox via the backend's existing `/api/*/login`; callback `tdj://auth/<provider>?ticket=…` | same | current redirects |
| `tdj-folder` | `NSOpenPanel` folder pick → security-scoped bookmark in app support; list + read files over IPC as raw `ArrayBuffer` (Tauri 2 binary responses) → `decodeAudioData` | `UIDocumentPickerViewController(forOpeningContentTypes: [.folder])` → bookmark; iCloud files downloaded on demand | `showDirectoryPicker` / `webkitdirectory` |
| `tdj-cue` (pre-listen) | `AVPlayer.audioOutputDeviceUniqueID` (or a second `AVAudioEngine` bound to a chosen CoreAudio device) plays the cue track on the headphones device; device list + hot-plug events | `AVAudioSession` multi-route with a ≥ 4-channel USB interface (channels 3/4 = cue); otherwise **split-cue mode** (room in L, cue in R, mono, through a Y-splitter — done in Web Audio with a `ChannelMergerNode`, works everywhere) | `AudioContext.setSinkId` → `HTMLMediaElement.setSinkId` → split-cue |
| `tdj-spotify` | spike S1: Web Playback SDK in WKWebView; else **Connect mode** (Web API `/me/player/*` driving the Spotify desktop app as a device) | Spotify **iOS SDK (App Remote)**: plays in the Spotify app, TDJ sends play/pause/seek/queue by URI, gets player state; SSO login through the Spotify app | Web Playback SDK |
| `tdj-system` | save panel for exports, `NSPrintOperation` print, `IOPMAssertion` keep-awake, `MPNowPlayingInfoCenter` + remote commands, menu bar + shortcuts (⌘↩ compose, ⌘E export, Space play/hold, ⌘. emergency stop) | share sheet for exports, `isIdleTimerDisabled`, Now Playing, hardware-keyboard shortcuts, `AVAudioSession(.playback)`, background audio mode | `<a download>`, Wake Lock, Media Session |
| `tdj-acp` (macOS DMG build) | see r22-acp-plan.md | — (remote/paired bridge only) | localhost bridge |

**Auth handoff without storing anything server-side** (phase 1, remote origin): the system browser sheet and the web view have separate cookie jars. The backend callback (new `?client=app` branch) seals the token set exactly as it does for the cookie, then wraps it in a 60-second, single-use **ticket** (the sealed blob encrypted again with an expiry; stateless, nothing written to DynamoDB/SSM) and redirects to `tdj://auth/<provider>?ticket=…`. The app loads `https://<backend>/api/app/redeem?ticket=…` in the web view, which sets the normal first-party cookie. The custom scheme is fixed and the redirect target is never taken from the request (no open redirect). BYOK model keys move from localStorage to the Keychain in the apps (sent as today's per-request headers).

**Spotify, honestly** (Settings copy must say this):
- macOS: in-app Spotify audio only if spike S1 passes; otherwise TDJ is the controller and Spotify plays in the Spotify app (Connect). Spotify audio is DRM-protected in every mode, so TDJ's Web Audio processing (normalisation, fades through gain nodes, meters) never applies to Spotify tracks — that is already true on the web, where the SDK only exposes `setVolume`.
- iPadOS: Spotify plays in the Spotify app through App Remote. No volume API → no fades/normalisation for Spotify sides, cortina fades only for local files and previews; "next at gap" uses the end-of-track state from App Remote (±0.5 s, not sample-accurate). Pre-listen of Spotify tracks is impossible (one Spotify stream per account) → pre-listen uses the 30 s Deezer/Spotify preview or the local file.
- Premium is required for any playback control; the Development Mode 5-user cap (docs/DEPLOY.md) applies to app logins too. The Spotify dashboard needs the iOS bundle ID and the `tdj://spotify-callback` redirect added (APPLE_SETUP.md §7).
- **Primary booth source on iPad = local files** (Files app folder) with the full Web Audio engine; Spotify is the second source, previews the rehearsal mode — the same hierarchy as the web Booth.

## 7. CI design

### 7.1 Workflows

**`native-check.yml`** — on PRs touching `apps/native/**` or `apps/web/src/lib/native/**`. `ubuntu-latest`: install webkit2gtk/libsoup deps, `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` for the core and desktop plugins, `vitest` for `store/limits.test.ts`. A **macOS compile-only** job (unsigned `tauri build --debug --bundles app` and `xcodebuild -scheme TDJ_iOS -sdk iphonesimulator build`) runs only when the PR has the label `apps:mac` or nightly on `main`, to protect macOS minutes.

**`release-apps.yml`** — `on: push: tags: ["v*"]` and `workflow_dispatch` (inputs: `platforms` = `mac-dmg,mac-appstore,ipad` default all; `channel` = `testflight` | `appstore-review`). `permissions: contents: write` (release assets only). `concurrency: release-apps`. Jobs:

1. `version` (ubuntu): marketing version from the tag (`v1.2.3` → `1.2.3`; dispatch without a tag → root `package.json` version + `-dev` for DMG names only), build number = `git rev-list --count HEAD` (fetch-depth 0; monotonic on `main`, identical for all three builds of a commit, which App Store Connect accepts per platform). Outputs both.
2. `mac-dmg` (macos-26, environment `apple-release`): checkout → pnpm + Node 22 (cache pnpm) → `dtolnay/rust-toolchain` with `aarch64-apple-darwin,x86_64-apple-darwin` → `Swatinem/rust-cache@v2` (workspaces `apps/native/src-tauri`) → temporary keychain + import `DEVELOPER_ID_APPLICATION_CERT_P12` (`apple-actions/import-codesign-certs@v3`, or `security create-keychain/import/set-key-partition-list`) → write `APP_STORE_CONNECT_PRIVATE_KEY` to `$RUNNER_TEMP/AuthKey.p8` → `pnpm --filter @tdj/native tauri build --target universal-apple-darwin --bundles app,dmg` with Tauri's built-in signing+notarisation env (`APPLE_SIGNING_IDENTITY="Developer ID Application: … (TEAMID)"`, `APPLE_API_ISSUER`, `APPLE_API_KEY`, `APPLE_API_KEY_PATH`) → verify: `codesign --verify --deep --strict`, `spctl -a -vvv -t install`, `xcrun stapler validate` → rename to **`TDJ-macOS.dmg`** (stable name) plus `TDJ-<version>-macOS.dmg` and `SHA256SUMS` → `gh release create v<version> --draft --generate-notes` (or upload to the existing tag release) → optional Tauri updater manifest `latest.json` signed with `TAURI_SIGNING_PRIVATE_KEY`. Release is published (draft → final) by a final job after all requested platforms succeed.
3. `mac-appstore` (macos-26, environment `apple-release`): import `APPLE_DISTRIBUTION_CERT_P12` + `MAC_INSTALLER_CERT_P12`, install `MAC_APPSTORE_PROFILE` as `embedded.provisionprofile`, build with `mac-appstore.plist` entitlements (sandbox, network.client, files.user-selected.read-write, files.bookmarks.app-scope, `com.apple.security.device.audio-output` not needed; no ACP spawning) → `productbuild --component TDJ.app /Applications --sign "3rd Party Mac Developer Installer: … (TEAMID)" TDJ.pkg` → `fastlane mac upload_testflight` (pilot, `pkg:`) or `xcrun altool --upload-package TDJ.pkg -t macos --apiKey $KEY_ID --apiIssuer $ISSUER` (altool upload with API key; `~/.appstoreconnect/private_keys/AuthKey_<KEYID>.p8`).
4. `ipad` (macos-26, environment `apple-release`): import `APPLE_DISTRIBUTION_CERT_P12`, install `IOS_APPSTORE_PROFILE` into `~/Library/MobileDevice/Provisioning Profiles/<uuid>.mobileprovision` (and the Xcode 16+ path `~/Library/Developer/Xcode/UserData/Provisioning Profiles/`), set version/build with PlistBuddy (or Tauri `bundle.iOS.bundleVersion`), `tauri ios build --export-method app-store-connect` with `CODE_SIGN_STYLE=Manual`, `CODE_SIGN_IDENTITY="Apple Distribution"`, `DEVELOPMENT_TEAM=$APPLE_TEAM_ID`, `PROVISIONING_PROFILE_SPECIFIER="TDJ iPad App Store"` (fallback S5: `xcodebuild archive` + `-exportArchive -exportOptionsPlist`) → `fastlane ios upload_testflight` (pilot with `app_store_connect_api_key`, `distribute_external: false`, changelog from `metadata/<locale>/release_notes.txt`). Cache `~/Library/Developer/Xcode/DerivedData` keyed on `Cargo.lock` + `gen/apple/project.yml`.
5. `publish` (ubuntu): un-draft the GitHub Release; job summary lists the TestFlight build numbers and the DMG URL `https://github.com/ArioMoniri/TDJ/releases/latest/download/TDJ-macOS.dmg`.
6. `submit-review` (ubuntu, only when `channel == appstore-review`, environment **`app-store`** with a required reviewer = the owner): `fastlane deliver` (runs on Linux — it only uses the App Store Connect API) with `submit_for_review: true`, `automatic_release: false`, `phased_release: true`, `submission_information` (export compliance: no non-exempt encryption; IDFA: false), metadata + screenshots from the reviewed `store-assets` artifact.

**`store-assets.yml`** — on PRs touching `fastlane/metadata/**`, `store/**`, `apps/web/src/**` (paths filter), and `workflow_dispatch` with `upload: true|false`. `ubuntu-latest` only: build + start the web app (`pnpm --filter @tdj/web build && start`, `TDJ_CONFIG_BACKEND=memory`), Playwright captures (§8), Remotion stills, `vitest store/limits.test.ts`, `fastlane run precheck` (ASC API) → upload `store-assets` artifact + a `contact-sheet.html` and post a PR comment linking it for designers. On `main` with `upload: true` (environment `app-store`): `fastlane deliver --skip_binary_upload --skip_app_version_update false` for metadata/screenshots only. No macOS minutes.

### 7.2 Signing approach

Manual signing with certificates + profiles as base64 secrets (predictable in CI, no Apple ID, no 2FA). Not chosen: `fastlane match` (needs a separate private certs repo + passphrase; useful later for multiple maintainers) and `xcodebuild -allowProvisioningUpdates -authenticationKey*` (cloud-managed signing; fine for iOS but Tauri's macOS path and `productbuild` still need local identities). Notarisation and all uploads use the **same App Store Connect API key** (notarytool and altool both accept `--key/--key-id/--issuer`), so no Apple ID app-specific password is needed. The release jobs run in GitHub Environment `apple-release` (secrets scoped to it, deployment branch rule `main` + tags `v*`), so a PR from a fork never sees them.

## 8. App Store assets pipeline

### 8.1 Tools checked

| Tool | Fit |
|---|---|
| fastlane `snapshot` + `frameit` | needs XCUITest UI tests in the Tauri Xcode project and a macOS runner per locale × device (expensive); frameit frames come from the `frameit-frames` repo, which lags new devices; `snapshot` has no macOS support. Keep **`deliver`** for upload only. |
| Open-source generators: `appshots` (PyPI, config + per-locale captions, deliver layout), `easyframecommand` (Swift, frameit-style), AppScreen (`YUZU-Hub/appscreen`, MIT, browser UI), Storeshot (MIT, agent-driven config), `asc-screenshots` agent skill, Open Screenshot Generator | all viable; most are young, self-reported, and either need a Mac (Swift) or a GUI. Re-check activity/licence before adopting. |
| **Playwright (already a devDependency; `scripts/capture-media.ts` already captures the app) + Remotion stills (already `apps/video`)** | captures the *real* UI at exact store pixel sizes on Linux, uses the repo's own fonts, brand and motion assets, renders captions in both languages from JSON, deterministic and reviewable as PNG diffs, zero macOS minutes. |

**Choice: Playwright + Remotion stills, uploaded with fastlane deliver.** It reuses two tools the repo already runs, works on `ubuntu-latest`, and the captured UI is the same UI the app's web view renders (phase 1 loads that exact origin), which satisfies guideline 2.3.3 (screenshots show the app in use). A macOS-runner sanity capture of the real app window (`screencapture -l <windowid>`) is added to `release-apps` as an artifact for comparison only.

### 8.2 Sizes App Store Connect requires (Apple's screenshot specifications page, read 2026-11-14)

- **Mac** (required): one of 1280×800, 1440×900, **2560×1600**, **2880×1800** (16:10). We ship 2880×1800 (Playwright viewport 1440×900, `deviceScaleFactor: 2`).
- **iPad 13-inch** (required if the app runs on iPad): portrait 2064×2752 or 2048×2732; landscape **2752×2064** or 2732×2048. We ship landscape 2752×2064 (viewport 1376×1032 @2×) — the Booth is a landscape tool — plus an optional portrait set. 12.9-inch (2nd-gen iPad Pro only) falls back to the scaled 13-inch set.
- 1–10 per device size and locale; PNG/JPEG, **no alpha** (Remotion renders with an opaque background; the pipeline checks with `sharp`/`pngjs` that there is no alpha channel and that dimensions match exactly — a one-pixel miss is rejected).
- iPhone sizes are not needed while the iOS build is iPad-only (`TARGETED_DEVICE_FAMILY=2`). In App Store Connect → Pricing and Availability, turn **off** "Make this app available on Apple silicon Macs" for the iPad app, because the native Mac build exists.
- App previews (video, optional): 15–30 s, Mac 1920×1080; iPad 13" 1200×1600 / 1600×1200 — `apps/video` can render these later from the same scenes.

## 11. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Spotify Web Playback SDK does not run in WKWebView (certain on iPad, unknown on Mac) | high | Spotify-in-app audio missing | iOS SDK App Remote on iPad; Connect mode / spike S1 on Mac; Electron-castlabs Mac fallback; local files are the primary booth source; honest Settings copy |
| No fades/normalisation/sample-accurate gaps for Spotify sides on iPad | certain | lower booth quality with Spotify | say so in the UI; recommend local files; "next at gap" with ±0.5 s tolerance |
| No `AudioContext.setSinkId` in WebKit; iPad has one output route | certain | pre-listen needs native code or hardware | `tdj-cue` (AVPlayer device on Mac, multi-route USB on iPad), split-cue mode as universal fallback |
| Web Audio drop-outs on iPad during a 4 h night (interruptions, lock screen, thermal) | medium | silence on the floor | spike S3; `AVAudioSession` playback + interruption handling; native player fallback; emergency stop + manual resume UI |
| App Review 4.2 / 2.5.2 for a remote-origin shell | medium | rejection | native plugins provide clear native value; phase 2 bundled UI before public release; TestFlight internal is not reviewed |
| Google blocks OAuth in web views | certain | login fails | `ASWebAuthenticationSession` + ticket handoff (§4) |
| WebKit ITP / storage eviction of IndexedDB | low–medium | lost history/overrides | spike S4; native mirror; server DB rows when enabled |
| Mac App Store sandbox forbids spawning local agents | certain | ACP local agents only in DMG build | DMG build spawns; MAS build connects to a user-run localhost bridge (r22-acp-plan.md) |
| macOS minutes on a private repo (10× multiplier) | depends on visibility | cost | macOS jobs only on tags/dispatch/label; Linux for metadata, screenshots, Rust checks; caches |
| Tauri iOS signing quirks in CI | medium | failed uploads | S5; committed `gen/apple`; ExportOptions.plist fallback with `xcodebuild` |
| Certificate/profile expiry (certs 1 yr Developer ID 5 yr, profiles 1 yr) | certain over time | release fails | APPLE_SETUP.md renewal calendar; workflow step warns 30 days before expiry (`openssl x509 -enddate`, profile `ExpirationDate`) |
| Turkish UI not ready for screenshots | high (until ROADMAP §7) | tr screenshots in English UI | Turkish captions now, automatic switch when `?lang=tr` lands |
| Concurrent edits by another engineer in `apps/web` | high | merge conflicts | all app work in new folders; web changes limited to the additive `lib/native/` adapters and feature-detected branches |
